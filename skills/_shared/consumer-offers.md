# Consumer offers

The offer bodies for first-run condition 8.
[`first-run.md`](first-run.md) carries the cheap-path check and the routing;
this file is where the operator actually answers, and where the committed
writes are recorded. It ships inside the plugin.

## Offer (a): `ci.gate_command`

Record the repo's local CI gate command so the deterministic merge gate can
stamp a passing run against the head.

- **Suggest the repo's own local CI script** if one exists at the repo root (in the three-pillars dev repo, `scripts/ci-local.sh`) —
  a repo that ships it already has a local CI entry point. Otherwise **suggest the recorded or discovered test command**
  (the `test.command` recorded by `/tp-test-setup`, or the command
  `iteration_lane.discover_test_command` resolves).
- The operator may supply any other command. The gate runs it through
  `ci_gate_run.py`, which stamps the head on rc 0 and refuses the PR stamp
  otherwise.
- **Check the ignore rules for the command's output.** The stamp needs a
  clean tree at the start of every run (`git status --porcelain
  --untracked-files=all`, untracked files included), so a gate command that
  leaves un-ignored output is refused: test/bytecode cache output
  (`__pycache__/**/*.pyc`, `.pytest_cache/`, `.coverage`) is stamped once,
  reported, and refused on the next run; any other new untracked output
  (`build/`, `dist/`, a generated `.py`) refuses the run that creates it.
  Before recording the command, check `.gitignore`
  for `__pycache__/`, `.pytest_cache/` and the project's build output
  (`git check-ignore -q <path>` per entry), and name the missing ones in the
  offer. Adding them is part of the operator's confirmed answer — append the
  confirmed lines to `.gitignore` and commit it with the config write; never
  edit `.gitignore` without that confirmation. A declined ignore rule is
  fine: `ci_gate_run.py` names any leftover output and the refusal lists the
  paths.
- The committed write goes through the shipped writer:
  `repo_config_load.py set ci.gate_command "<json-string>"` (a JSON
  `null` value is a recorded "no"; an absent key is "never offered").

## Offer (b): the commit guard

A `pre-commit` and a `commit-msg` hook, installed into the repo's git hooks
dir, that runs the framework's commit-guard checks at commit time.

### Sub-asks (the operator answers each)

- **file-size caps (default: no)** — the pre-commit step 4 in
  `commit_guard.run` runs `file_size_guard.main` only when
  `commit_guard.file_size` is `true`. Opt-in, because it is the one arm
  that can grow a commit's runtime and the caps are otherwise advisory
  (see [`file-size-caps.md`](file-size-caps.md)).
- **deny rules (default: yes)** — when the `commit_guard.deny_no_verify`
  key is `true`, merges `Bash(git commit --no-verify:*)` and
  `Bash(git commit -n:*)` into the repo's `.claude/settings.json`
  `permissions.deny`. The install is idempotent and never removes the
  operator's own entries. The scope is Claude-run commits only; a human
  can still pass `--no-verify` (the offer says so).

### The isolation scope, and its ways out

`worktree_isolation_guard --assert-own-worktree` (pre-commit step 2)
refuses every commit from the base checkout while any `tp/*` design
worktree exists, not only design files. The one exception is a staged set
that is only `three-pillars-docs/tp-designs/orchestration/` (the seat's
own paper trail). The ways out, stated plainly:

- commit inside the worktree (the guard's own path), or
- finish or release the design (`/tp-design-complete` /
  `/tp-design-release`) so the design worktree is removed.

### The `commit-msg` hot-patch refusal

`commit-msg` runs `hot_patch_check --commit-msg` on the pending commit. A
`hot-patch:`-trailered commit that stages a file in the lane's exclusion
set (or exceeds the diff cap) is refused, and the commit does not happen.
Ordinary commits with no `hot-patch` trailer are inert.

### `<hook>.legacy` placement

If the target hook is a pre-commit-framework script (`File generated by
pre-commit` + `hook-impl`), the block lands in `<hook>.legacy`, not the
hook itself. `pre-commit install` rewrites the generated script whole
(only *foreign* hooks are moved to `.legacy`), so a block inside the
generated script would vanish at the next install; `<hook>.legacy`
survives. The offer names the placement so the operator is not surprised
by a `.legacy` file appearing in the hooks dir.

### The empty-range and no-gate-command residuals

- **Empty range.** On the default branch with no `origin`, the backstop
  range (`<base>..HEAD`) is empty and the `pre-commit` arm (b) checks
  nothing there. `commit-msg` still checks each new commit; an amended
  trailered commit is caught only by review.
- **No gate command.** In a repo with no `ci.gate_command`, an amended
  commit that is pushed with no later local commit is caught only by
  review. The gate-stamp path (`ci_gate_run.py`) is not in play without
  a gate command.

### The pre-install overdue-obligation listing

`apply` runs `hot_patch_check --ledger-only` once, before the install
completes, and prints each overdue SHA (a trailered commit with no
ledger entry) with the remedy — "append its entry to
`three-pillars-docs/tp-designs/orchestration/hot-patches.md`" — and the
note that the first commit after the install is refused until the entry
is recorded. The install proceeds anyway; the obligation is real.
Under `--auto`, the list is logged to `decisions.md`.

### The committed writes

- **Yes**: the install is `commit_guard.py apply [--file-size]
  [--deny-no-verify]` (the flags match the operator's sub-ask answers),
  then
  `repo_config_load.py set commit_guard.offered_at <now>` is written by
  the offer itself before the answer (so the offer's suppression is
  sticky regardless of the answer).
- **First "no"**: `repo_config_load.py set commit_guard.declined true`
  (the committed config, sticky — never re-asks). The committed
  `commit_guard.applied_at` is written only by `commit_guard.py apply`.
- **Clone-level "no"** (the cheap-path re-offer, when the committed
  config says installed but this clone is not): `commit_guard.py decline`
  writes only the per-clone marker
  `<git-common-dir>/three-pillars/commit-guard-declined`; it does not
  touch the committed config, so one teammate's answer does not change
  the repo's.

### Refusals

If `apply` finds a cause (the hooks dir is outside the common dir, a
non-shell shebang, a non-executable hook / generated script / `.legacy`,
or a generated script without `--hook-dir`), it writes no hook, returns
two snippets (one for `pre-commit`, one for `commit-msg`) the operator
can add by hand, and records the cause per clone in
`<git-common-dir>/three-pillars/commit-guard-manual`. The committed
config is not touched, so a teammate's clean clone is still offered the
install.

### The refusal marker

When `commit-guard-manual` exists, the cheap path runs
`commit_guard.py status`:

- effective (the operator added the snippets) → silent;
- the recorded cause still holds → one loud line only; the marker
  suppresses any re-offer in this clone;
- the cause no longer holds (e.g. a global `core.hooksPath` was removed)
  → delete the marker and make the offer again.

### `--auto`

Never installs, never writes the committed `commit_guard` block, and logs
a `[first-run]` entry to `decisions.md` with the overdue-obligation list
(the pointer and the stale-block refresh are the only writes that do
happen; they touch only files the guard already owns).

## Offer (c): the `.handoffs/` ignore rule

The round-bundle JSON under every design's `.handoffs/` is never committed, but the cold-resume worklists (the `.md` files `/tp-run-full-design` commits) stay tracked, so the rule is a pair per root: ignore everything under `.handoffs/` and re-include the `*.md` worklists. Both roots are needed — design-complete's `git mv` carries the bundles into `completed-tp-designs/{name}/.handoffs/`.

- **Check first**: run `python3 "$TP_ROOT"/skills/_shared/handoffs_ignore.py check` — it exits 0 when all four rules are already present (the offer is settled, no prompt) and 1 otherwise. On 1, show exactly these four lines (both roots):

  ```
  three-pillars-docs/tp-designs/*/.handoffs/*
  !three-pillars-docs/tp-designs/*/.handoffs/*.md
  three-pillars-docs/completed-tp-designs/*/.handoffs/*
  !three-pillars-docs/completed-tp-designs/*/.handoffs/*.md
  ```

- **Confirmed**: `python3 "$TP_ROOT"/skills/_shared/handoffs_ignore.py apply` appends only the missing lines under one comment (idempotent) and prints them. The append happens on a confirmed answer only — never edit `.gitignore` for this rule without that confirmation; commit it with the config write.
- **No**: `repo_config_load.py set gitignore.handoffs_declined true` (the committed config, sticky — never re-asks).
- **`--auto`**: never writes `.gitignore` or the config; logs a `[first-run]` entry to `decisions.md` naming the four lines (the same shape as the branch-protection auto-skip).

## Offer (d): local client timeouts

Local-model runs stream slowly, and Claude Code's default client timeouts can cut a long local turn off mid-response. The offer adds four `env` keys to the repo's `.claude/settings.json`: `CLAUDE_BYTE_STREAM_IDLE_TIMEOUT_MS`, `CLAUDE_STREAM_IDLE_TIMEOUT_MS` and `API_TIMEOUT_MS` (1800000 each), and `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS` (1500000). It is wanted only when `local_implement.enabled` is true or a `models` entry is `local-*`. The answer is recorded under `local_implement.client_timeouts` (`applied_at`, `declined`, `values`).

- **Check first**: `python3 "$TP_ROOT"/skills/_shared/local_timeouts.py offer` (`--claude-version X.Y.Z` overrides the `claude --version` probe) prints one JSON object (`wanted`, `settled`, `version`, `version_ok`, `plan`) and writes nothing. `wanted: false` or `settled: true` means there is nothing to offer.
  - A malformed settings file (not a JSON object, or an `env` that is not one): the command exits 2 with one line, nothing written. Show that line and stop; the operator fixes the file.
  - Empty `plan.add` and empty `plan.keep` means the values are already in place, so there is no prompt. An interactive run still records `applied_at` through `apply` (a config write only).
- **Version**: `version_ok: false` is a notice only, nothing recorded: print one line, "needs Claude Code ≥ 2.1.242, found X", and the offer comes back once the client is upgraded. `version_ok: null` means the version is unknown (the probe failed); say so, and the body still offers the change.
- **The offer**: show `plan.diff` (`plan.creates_file` is true when the settings file does not exist yet), and list each `plan.keep` key as "kept, your value": a key already set to another value is never overwritten. Note that the change takes effect from the next Claude Code session: the settings `env` is read at session start, and the subagents of that session are expected to inherit it.
- **Yes**: `python3 "$TP_ROOT"/skills/_shared/local_timeouts.py apply` adds only the `plan.add` keys (every other key stays as it was) and records `applied_at` and `values`; then commit `.claude/settings.json` with `.three-pillars/config.json`.
- **No**: `python3 "$TP_ROOT"/skills/_shared/local_timeouts.py decline` records `declined: true` (sticky, never re-asks).
- **`--auto`**: never writes the settings file or the config. It logs a `[first-run]` entry to `decisions.md` with `plan.diff` (Confidence: Medium), and logs nothing when `plan.add` is empty.

## Offer (e): test-running pre-commit hook

A repo whose `pre-commit` hook runs the test suite refuses the framework's
red-then-green protocol: the `Red:` commit's test fails by design, so the
hook refuses that commit — and `--no-verify` is denied (Offer (b)). The
offer moves the test run to the `commit-msg` side, where the red gate
(`red_commit_gate.py`) lets a `Red:` commit through only when the failing
test files are exactly the staged ones.

- **Check first**: run `python3 "$TP_ROOT"/skills/_shared/hook_detect.py --root .`
  — it prints JSON entries `{kind, path, wired}` for every test-running
  hook it found (`git-hook`, `pre-commit-framework`, `husky`, `lefthook`).
  An empty list, or every entry already `wired`, means there is nothing to
  offer.
- **The offer**: show each entry and say why it is a problem (the sentence
  above). Then show the one-line snippet from
  `python3 "$TP_ROOT"/skills/_shared/red_commit_gate_cli.py snippet --test-cmd '<the detected hook's test command>'`.
  **APPEND** it to the existing `commit-msg` hook — the commit guard's
  block lives there, so never replace the file. That file is the
  `commit-msg` in the hooks dir `git rev-parse --git-path hooks` prints, or
  `.husky/commit-msg` for husky, or a `commit-msg` entry for lefthook or
  the pre-commit framework. Then drop the test step from the pre-commit
  side, so the suite runs once per commit, not twice.
- **Yes**: wiring happens only on a yes — by the operator, or by Claude
  with the operator's confirmed answer, never silently.
- **No**: nothing is recorded; the offer returns at the next
  `/tp-test-setup`.
- **`--auto`**: never wires; logs a `[first-run]` entry to `decisions.md`
  with the detected entries.
- **Where it is raised**: `/tp-test-setup` raises it. First-run raises it
  only when its `## Consumer offers` section already runs for another
  unsettled offer — never on the hot path.

## Offer (f): generated lockfiles

A lockfile such as `package-lock.json` or `uv.lock` that both sides of a
base-sync changed conflicts as a whole file. Declaring it as a generator lets
`/tp-merge-from-main` rebuild it from its manifest instead of deferring.

- **Check first**: run `python3 "$TP_ROOT"/skills/tp-merge-from-main/scripts/generator_catalog.py detect --repo . --json` (optionally narrowed with `--only <path>`, repeatable). It prints a JSON list of `{path, tool, tool_on_path, entry}` for tracked lockfiles the catalog knows (`package-lock.json`, `uv.lock`) that are not yet declared and not yet offered. It writes nothing; an empty list means there is nothing to offer.
- **The offer**: show each match, whether its `tool` is on PATH, and the exact write argv from `entry`, and say plainly that the rebuild uses the network (the package manager may fetch metadata) and runs inside the repo.
- **Yes**: at the `/tp-merge-from-main` site the base-sync merge is still open and git refuses any commit while a file is unmerged, so abort it first with `git merge --abort` (nothing is lost: the offer comes before any hand resolution and the driver redoes its auto-resolutions on the re-run). Then run `python3 "$TP_ROOT"/skills/tp-merge-from-main/scripts/generator_catalog.py accept --repo . --paths <path> [<path> ...]` — it adds the generator entries and the offer record to `.three-pillars/config.json` — commit that file as `config: declare generated lockfiles`, and re-run `/tp-merge-from-main`, which now rebuilds the lockfile. An operator who would rather keep the merge open runs `accept` and the config commit after the merge commit instead. At the first-run site no merge is open: run `accept` and commit the file directly. Only on a confirmed yes, never silently.
- **No**: run `python3 "$TP_ROOT"/skills/tp-merge-from-main/scripts/generator_catalog.py decline --repo . --paths <path> [<path> ...]`; it records `merge_from_main.generator_offer` (`offered_at`, `declined`, `offered_paths`) so the same lockfile is not offered again.
- **`--auto`**: never writes; appends a `[tp-merge-from-main]` suggestion holding the match's `entry` to `decisions.md`.
- **Where it is raised**: `/tp-merge-from-main` raises it after step 4's report, for the deferred lockfiles. First-run raises it only when its `## Consumer offers` section already runs for another unsettled offer, never on the hot path.

## Enforcer

`file_size_guard.py` is the file-size cap predicate the commit guard's
`pre-commit` step runs when `commit_guard.file_size` is on. The shipped caps table lives in
[`file-size-caps.md`](file-size-caps.md); enforcement applies only when
the commit guard is installed with the file-size sub-ask on (see the
sub-asks above).
