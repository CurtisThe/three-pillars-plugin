# Spike Learn

Read a completed spike's artifacts and synthesize learnings into proposed updates for project docs and downstream designs. Doc updates go into the spike's fragment (`skills/_shared/living-doc-fragments.md`), never a living doc.

**Argument**: `{spike-name}` (required) — must match an existing directory under `three-pillars-docs/tp-designs/`.

## Prerequisites
- `three-pillars-docs/tp-designs/{spike-name}/spike-results.md` must exist. If not, tell the user to run `/tp-spike-results {spike-name}` first and stop.

## Steps

0. **Run first-run preflight** per skills/_shared/first-run.md.

1. **Validate `{spike-name}`** per `skills/_shared/validate-name.md`.
2. **Read the full spike directory**: `design.md`, `plan.md`, `spike-results.md`, and any code or demo artifacts referenced.
3. **Read project docs** per `skills/_shared/read-project-docs.md`.
4. **Design Inventory row → the fragment**: write the doc changes into `three-pillars-docs/changes/{spike-name}.md`: create it when absent (frontmatter `slug`, `kind: spike`, `date`), else edit it in place (rewrite a registration `+` row, never `-` it), and set `date` and `learned` to today. Under `## Roadmap`, in the `### <heading holding the row>` block, replace the `{spike-name}` row (`- <old>`, `+ <new>`; a row not in the table is a lone `+`) with a **short label + link** per `skills/_shared/living-doc-format.md` (e.g., `Done — GO (PR #NN) — [results](completed-tp-designs/…/spike-results.md)` or `Done — PARTIAL` or `Done — NO-GO`). Keep What and Status cells short — narrative belongs in the linked spike-results or seed.
5. **Current Focus → the fragment**: if the roadmap has a `## Current Focus` table, propose `-`/`+` lines in a `### Current Focus` block under `## Roadmap`, based on the spike verdict:
   - **GO/PARTIAL**: Remove or update the spike's row. Update "Blocked By" on any row that listed this spike as a blocker — clear the blocker and update "Next Action" to the now-unblocked step (e.g., "Blocked on S9" → "`/tp-design-detail` — ready to proceed").
   - **NO-GO**: Update the spike's row to reflect the verdict. Mark any dependent rows as blocked with an explanation.
   - **Promote** new items to Current Focus if the verdict unblocks work that wasn't previously listed.
6. **Propose updates** into the fragment's other sections, following `skills/_shared/propose-doc-edits.md` (show the lines, get confirmation): `## Architecture` (`### <heading in architecture.md>` blocks), `## Known issues — add` (a new Low is an `L-new-` block) and `— resolve`, and the History line (`+ - YYYY-MM-DD — summary.` under 800 non-ws chars, below that doc's History heading). Explain why the spike findings motivate each. The compile bumps `*Last updated:*` and rolls History and caps over. **A spike with no doc change still writes the fragment, frontmatter only.** Then run `python3 "$TP_ROOT"/skills/_shared/changes_fragment.py validate three-pillars-docs/changes/{spike-name}.md --repo-root . --require-learned`; on exit 1 fix the section it names and re-run.
   - **Legacy slug** (in `.three-pillars/living-doc-legacy.txt`; its PR already edits the docs): edit the docs directly, keep the fragment frontmatter-only, and per `skills/_shared/living-doc-format.md` update `*Last updated:*` and add the History line at the top.
   - **Roll the doc to its cap in the same commit** (legacy slug): for each living doc you wrote, run `python3 "$TP_ROOT"/skills/_shared/doc_rollover.py --doc <repo-relative doc>` and keep the condensed form per `skills/_shared/living-doc-format.md` §Condensed shape and caps (one bullet or row per item, history to the archive); stage the doc's archive in the same commit.
   - **Fragility-class findings → rule proposal**: when the spike's results or PR-loop trail holds a finding whose `fragility_class` is in `finding_fields.FRAGILE_CLASSES` (per `skills/_shared/test-fragility.md`), draft a per-repo fragility rule proposal (kind, params, reason) alongside a drafted `## Known issues — add` block, and put both in this step's approval: a call maps to `forbidden-call`, a named collection literal to `forbidden-literal-name`, a file read and asserted on to `forbidden-read-assert`. **Interactive**: on approval, run `python3 "$TP_ROOT"/skills/_shared/fragility_repo_rules.py add --kind <kind> --params <json> --reason <text> --approved-by <operator>` and stage `.three-pillars/fragility-rules.json` with the step-11 learn commit. **`--auto`**: never run `add` — write the proposal as a Decision Entry (`Confidence: Low`, "needs operator approval") instead, since an approval cannot be self-granted.
7. **Learn-verification (advisory)**: run `python3 "$TP_ROOT"/skills/_shared/verify_learn.py --range {default}...tp/{spike-name} --json` (where `{default}` is the base branch — usually `master`). It reports `three-pillars-docs/**` lines (living **and** `completed-tp-designs/`) that still name a symbol or file this spike **retired** (deleted/renamed in the diff) — the "learn ran ≠ docs match as-built" gap. Treat any hit as a propagation miss: fold the scrub into the step-6 doc updates. **Advisory only** — the helper always exits 0 and fails open; never block on it. Surface remaining hits in the step-12 report (and, in `--auto`, append them to `decisions.md`). Range note: `{default}...tp/{spike-name}` (three-dot) diffs merge-base→`tp/{spike-name}`, surfacing *this spike's* deletions — not the reverse.

   Legacy slug only, finally roll each living doc updated in step 6: run `python3 "$TP_ROOT"/skills/_shared/history_rollover.py --doc <repo-relative doc>` (default keep 15; no History section or missing doc → it does nothing and says so). The doc's archive is staged in the step-11 commit.
8. **Scan for affected downstream designs**: Read all `design.md` files under `three-pillars-docs/tp-designs/` (excluding the current spike). Match architecture decision keywords from `spike-results.md` against each design's Scope and Entities sections. For each affected design, also check whether its declared dependencies or parent references include the current spike — if so, note whether the spike verdict changes the dependency status.
9. **Propagate NO-GO to dependent rows**: If the verdict is **NO-GO** and step 6 found designs that declare this spike as a dependency (via Dependencies section or Parent field), propose `-`/`+` lines for those designs' Design Inventory rows in the fragment's `## Roadmap`. Set their status to include a blocked annotation (e.g., "Designed" → "Blocked — `{spike-name}` NO-GO"). Show each proposed row change and get user confirmation. This ensures that `/tp-plan` will see the blocked status when it checks upstream dependencies, closing the feedback loop.
10. **Vision drift check (do not auto-propose vision edits)**: Compare `spike-results.md` against `three-pillars-docs/vision.md`. A spike can legitimately surface that a vision assumption was wrong — for example, a "GO" that reveals the problem is bigger than the vision framed it, or a "NO-GO" that invalidates a principle the vision depends on. If you find a genuine tension, **flag it** to the user with a specific citation (which finding, which vision bullet) and recommend `/tp-docs-update vision` as an explicit follow-up. **Do not propose vision edits directly from this skill.** Spike verdicts feed the vision via a deliberate human gate, not automatically.
10b. **Run retro (this run's framework friction; protocol, consent and board contract in `skills/_shared/run-retro.md`).** `<design dir>` is `three-pillars-docs/tp-designs/{spike-name}`, `<scratch>` the run's scratch dir. It proposes and files; it never edits a skill. Fail-open: a non-zero exit logs one line and the skill goes on to step 11.
    - `python3 "$TP_ROOT"/skills/_shared/run_retro.py known-items --repo . --out <scratch>/known-items.json`, then `python3 "$TP_ROOT"/skills/_shared/run_retro.py draft --design-dir <design dir> --known-items <scratch>/known-items.json`; it prints `review_needed`.
    - Only when `review_needed`: `python3 "$TP_ROOT"/skills/_shared/run_retro.py review-prompt --design-dir <design dir> --known-items <scratch>/known-items.json` prints a brief path. Run `Agent(subagent_type=agent_ref("tp-readonly-auditor"), model="opus")` on it and save the reply as `<scratch>/verdicts.md`. Otherwise skip the reviewer and drop `--verdicts`.
    - `python3 "$TP_ROOT"/skills/_shared/run_retro.py file --design-dir <design dir> --verdicts <scratch>/verdicts.md --board <automated_upgrades|none> --notion-skill <present|absent>`. Use `--board automated_upgrades` only when the repo's notion-ops config has an `automated_upgrades:` block, else `none`; `--notion-skill present` only when `notion-file-upgrade-request` is in the session's skill list. With no board it writes fallback seeds (the consumer-repo path) and prints each seed path it wrote or changed: stage exactly those in step 11, never a glob.
    - Board path (`file` printed an outbox with entries): interactive, show `retro-outbox.json` and ask once; on a decline run `python3 "$TP_ROOT"/skills/_shared/run_retro.py note --design-dir <design dir> --title declined`, post nothing and skip `record`. `--auto`: post, never prompt. Post one `/notion-file-upgrade-request --package <package> --type <Bug|Idea> --source-run <design-slug> --root-cause-group <text> --evidence <pointer>... --reviewer-verdict <accept|merge-with> --version <version> [--design <design>] [--rrsi-flag <flag> ...] [--recurrence <n>]` per `retro-outbox.json` entry (the skill's own doc in notion-ops-skills is the spec), its flags taken from that entry's `payload`: `--source-run` is the design slug, `--reviewer-verdict` is the word before the first `:` of the payload's reviewer verdict, `--evidence` and `--rrsi-flag` repeat once per list item (leave `--rrsi-flag` out when the list is empty). Each call replies one line, `filed: <action> <url>` or `not filed: <reason>` (normal when the teamspace has not enabled automated upgrades). Write the reply lines as `<scratch>/filed.json`, `[{slug, reply}]` with the entry's `slug` and the line verbatim (leave an error out: its entry stays in the outbox), then run `python3 "$TP_ROOT"/skills/_shared/run_retro.py record --design-dir <design dir> --filed <scratch>/filed.json`. `record` seeds each `not filed` entry on its own and prints `seeds`: stage exactly those in step 11.
11. **Commit the fragment** per `skills/_shared/commit-after-work.md`. Artifact paths to stage (include only those actually modified in steps 4–10b):
    - `three-pillars-docs/changes/{spike-name}.md`, the only living-doc path (the guard refuses a shared living doc)
    - Legacy slug only, the docs its step-6 edits modified: `three-pillars-docs/product_roadmap.md`, `architecture.md`, `known_issues.md`, `known_issues_resolved.md` (**move** a resolved entry there verbatim, never mark it in place), and the rollover archives `three-pillars-docs/architecture_archive.md` and `three-pillars-docs/product_roadmap_archive.md` (when the rollover moved entries)
    - `.three-pillars/fragility-rules.json` (when step 6's fragility-class rule proposal was approved and `fragility_repo_rules.py add` ran)
    - Any downstream `three-pillars-docs/tp-designs/{other}/design.md` files whose Design Inventory row was updated with a blocked annotation per step 9
    - `<design dir>/decisions.md`, `<design dir>/retro-findings.json` and `<design dir>/retro-outbox.json` (when step 10b wrote them), plus the exact seed paths `file` and `record` printed (new seeds and any seed that got an evidence line)
    Do NOT stage `three-pillars-docs/vision.md` — this skill never auto-edits vision. Commit message: `Learn: {spike-name} spike`.
12. **Report**: Summarize what was updated, what designs are affected, any vision tensions flagged, and suggest `/tp-design-complete {spike-name}` as the next step.

## Rules
- Follow `skills/_shared/propose-doc-edits.md` for all doc updates.
- If the parent design (from design.md Parent field) exists, always include it in the affected designs scan regardless of keyword matching.
- If docs don't exist, suggest `/tp-docs-init` but don't block — the user may want to see affected designs without updating docs.
- Keep proposed edits surgical — update specific sections, don't rewrite entire docs.
- **Never auto-edit `three-pillars-docs/vision.md`.** Flag tensions, recommend `/tp-docs-update vision`, let the user decide.

## Auto Mode

`--auto` is a **Shape B (Generator)** per `skills/_shared/auto-mode.md`. It exists so `/tp-spike-auto` (Step 5.5) can close out a spike unattended — enforced closeout-before-terminal, replacing the old deferred-learn. It derives the doc updates from `spike-results.md` + the spike artifacts without Q&A.

In `--auto`:
- **Run steps 4–8, 10b and 11–12 without prompting** — derive the Design Inventory / Current Focus / doc lines and write them into the fragment; self-assess each judgment call (Confidence: High/Medium/Low) and log it to `three-pillars-docs/tp-designs/{spike-name}/decisions.md` with the `[tp-spike-learn]` prefix (canonical init/append snippet in `auto-mode.md`).
- **Step 7 (learn-verification) still runs** — append any flagged stale refs to `decisions.md`; advisory, never blocks (the helper always exits 0).
- **Step 10 (vision drift check): log tension to `decisions.md` and continue.** **Never** propose, draft, or apply any edit to `three-pillars-docs/vision.md` — the sticky-vision principle holds even with no human in the loop. Append a Decision Entry (Confidence: Low) describing the specific finding ↔ vision-bullet tension; the user reviews it.
A known issue you file here uses a placeholder ID, numbered later (see `skills/_shared/issue-id-placeholders.md`).

- **Step 10b (retro) still runs.** Under a configured board it posts without asking, so a decline never occurs; the CLI logs each id.
- **Step 11 (commit) still runs** — stage only the fragment `three-pillars-docs/changes/{spike-name}.md`, `decisions.md`, `retro-findings.json`, `retro-outbox.json`, the exact seed paths `file` and `record` printed, and any blocked-annotation downstream `design.md` rows (a legacy slug also its modified `product_roadmap.md`, `architecture.md`, `known_issues.md`, `known_issues_resolved.md`, `architecture_archive.md`, `product_roadmap_archive.md`) — never `vision.md`. Commit message stays `Learn: {spike-name} spike`.

**Contract: in `--auto`, this skill propagates spike findings into the project docs and runs learn-verify, every diff logged to `decisions.md`, never editing `vision.md`.**
