# Design Learn

Read a completed design's artifacts and synthesize what was built into proposed updates for project docs and downstream designs. Doc updates go into the design's fragment (`skills/_shared/living-doc-fragments.md`), never a living doc.

**Argument**: `{design-name}` (required) — must match an existing directory under `three-pillars-docs/tp-designs/` or `three-pillars-docs/completed-tp-designs/`. `--cheap-tier[=ab]` (optional, deprecated) changes nothing: the step-7 cheap-tier drafts run in every invocation, per `skills/_shared/cheap-dispatch.md`, and `<mode>` is `on` (`/tp-run-full-design` forwards bare `--cheap-tier`).

## Prerequisites
- `design.md` and `implementation-audit.md` (or at minimum `plan.md` with all tasks Done) must exist. If not, tell the user what's missing and stop.

## Steps

0. **Run first-run preflight** per skills/_shared/first-run.md.

1. **Validate `{design-name}`** per `skills/_shared/validate-name.md`.
2. **Locate the design directory**: check `three-pillars-docs/tp-designs/{design-name}/` first, then `three-pillars-docs/completed-tp-designs/{design-name}/`.
3. **Read the full design directory**: `design.md`, `detailed-design.md`, `plan.md`, `implementation-audit.md`, and any `review.md` files.
4. **Read project docs** per `skills/_shared/read-project-docs.md`.
5. **Design Inventory row → the fragment**: write the doc changes into `three-pillars-docs/changes/{design-name}.md`: create it when absent (frontmatter `slug`, `kind: design`, `date`), else edit it in place (rewrite a registration `+` row, never `-` it), and set `date` and `learned` to today. Under `## Roadmap`, in the `### <heading holding the row>` block, replace the `{design-name}` row (`- <old>`, `+ <new>`; a row not in the table is a lone `+`) with a **short label + link** per `skills/_shared/living-doc-format.md` (e.g., `Done — PR #NN — [design](completed-tp-designs/…/design.md)`). Until the completion PR opens, write `Completion PR pending` (never free prose) in the Design Inventory status cell only (placement per `skills/_shared/living-doc-format.md`); Recent completions uses `Done — {pr}`.
6. **Current Focus → the fragment**: if the roadmap has a `## Current Focus` table, propose `-`/`+` lines in a `### Current Focus` block under `## Roadmap`:
   - **Remove** the completed design's row.
   - **Update "Blocked By"** on any row that listed this design as a blocker (clear it if this was the only one) and **"Next Action"** on any row whose next step changed (e.g., a dependent design can now proceed to `/tp-design-detail`).
   - **Promote** the next logical item if removing the row leaves a priority gap, from the Design Inventory designs whose dependencies are now satisfied.
7. **Propose updates** into the fragment's other sections, following `skills/_shared/propose-doc-edits.md` (show the lines, get confirmation): `## Architecture` (`### <heading in architecture.md>` blocks), `## Known issues — add` (a new Low is an `L-new-` block) and `— resolve`, and the History line (`+ - YYYY-MM-DD — summary.` under 800 non-ws chars, below that doc's History heading). Explain why the completed design motivates each. The compile bumps `*Last updated:*` and rolls History and caps over. **A design with no doc change still writes the fragment, frontmatter only.** Then run `python3 "$TP_ROOT"/skills/_shared/changes_fragment.py validate three-pillars-docs/changes/{design-name}.md --repo-root . --require-learned`; on exit 1 fix the section it names and re-run.
   - **Legacy slug** (in `.three-pillars/living-doc-legacy.txt`; its PR already edits the docs): edit the docs directly, keep the fragment frontmatter-only, update `*Last updated:*` and add the History line at the top per `skills/_shared/living-doc-format.md`. In the same commit run `python3 "$TP_ROOT"/skills/_shared/history_rollover.py --doc <repo-relative doc>` (keep 15), then `python3 "$TP_ROOT"/skills/_shared/doc_rollover.py --doc <repo-relative doc>` keeping the condensed form per `skills/_shared/living-doc-format.md` §Condensed shape and caps, and stage each doc's archive in the same commit. File a new Low with `python3 "$TP_ROOT"/skills/_shared/low_doc_parts.py target --chars <entry-chars> --create` (it names the part, creating `known_issues_low_2.md` when part 1 is near full), then set the `N Low issues →` line in `known_issues.md` to what `python3 "$TP_ROOT"/skills/_shared/low_doc_parts.py count` prints.
   - **Consumer-repo behaviour**: if `design.md` has a `## Consumer-repo behaviour` section, propose an `architecture.md` entry (an `## Architecture` block) recording what ships and how it behaves in a user's repo, so the floor this design shipped stays visible after archival.
   - **Fragility-class findings → rule proposal**: when the design's review, audit or PR-loop trail holds a finding whose `fragility_class` is in `finding_fields.FRAGILE_CLASSES` (per `skills/_shared/test-fragility.md`), draft a per-repo fragility rule proposal (kind, params, reason) alongside a drafted `## Known issues — add` block, and put both in this step's approval: a call maps to `forbidden-call`, a named collection literal to `forbidden-literal-name`, a file read and asserted on to `forbidden-read-assert`. **Interactive**: on approval, run `python3 "$TP_ROOT"/skills/_shared/fragility_repo_rules.py add --kind <kind> --params <json> --reason <text> --approved-by <operator>` and stage `.three-pillars/fragility-rules.json` with the step-11 learn commit. **`--auto`**: never run `add` — write the proposal as a Decision Entry (`Confidence: Low`, "needs operator approval") instead, since an approval cannot be self-granted.
   <!-- cheap-tier:docs_draft -->
   **Cheap-tier proposal drafts (never for `vision.md`; the loop is `skills/_shared/cheap-dispatch.md`).** Before writing each step-7 proposal, run `python3 "$TP_ROOT"/skills/_shared/cheap_tier_cli.py spec --slot docs_draft --root . --cheap-tier <mode> --probe --design {design-name}` in Bash with timeout 300000; a null rung means the proposal is written as today. Otherwise write a facts payload JSON (the doc, the section's current text, what changed and why, and every PR number and SHA it may cite), never the session context, and spawn `Agent(subagent_type=<spec.agent_ref>, model=<spec.model>, …)` to write one scratch file from it: the diff-style proposal as `**Before**`, `**After**` and `**Why**`.
   Check it with the `prose_shape` oracle: `python3 "$TP_ROOT"/skills/_shared/cheap_oracle_run.py check --slot docs_draft --artifact <A.json> --ctx <C.json>` (artifact `path`; ctx `kind` `docs_draft`, `root` `.`, `facts`). On `accept` the draft is the proposal, which the operator approves as today. A dropped draft means the proposal is written as today.
   Then run `python3 "$TP_ROOT"/skills/_shared/prose_oracle.py save-draft --root <design dir> --slot docs_draft --draft <draft> --final <a file holding the final text> --reviewed <operator approved>`; `--auto` means `--reviewed false`. Record the attempt per the dispatch doc; under `ab`, run its pure-slot pair and use neither arm.
   <!-- /cheap-tier -->
   <!-- cheap-tier:history_line -->
   **Cheap-tier History line (never for `vision.md`; the loop is `skills/_shared/cheap-dispatch.md`).** For each History line, run `python3 "$TP_ROOT"/skills/_shared/cheap_tier_cli.py spec --slot history_line --root . --cheap-tier <mode> --probe --design {design-name}` in Bash with timeout 300000; a null rung means the line is written as today. Otherwise spawn `Agent(subagent_type=<spec.agent_ref>, model=<spec.model>, …)` on a facts payload JSON (today's date, the doc, the one change to summarize, and every PR number and SHA it may cite), never the session context, to write one scratch file: the dated History line, shown with its doc's proposal.
   Check it with the `prose_shape` oracle: `python3 "$TP_ROOT"/skills/_shared/cheap_oracle_run.py check --slot history_line --artifact <A.json> --ctx <C.json>` (artifact `path`; ctx `kind` `history_line`, `root` `.`, `facts`). On `accept` it is the proposed line. A dropped draft means the line is written as today. Then run `python3 "$TP_ROOT"/skills/_shared/prose_oracle.py save-draft --root <design dir> --slot history_line --draft <draft> --final <a file holding the final text> --reviewed <operator approved>`; `--auto` means `--reviewed false`.
   Record the attempt per the dispatch doc; under `ab`, run its pure-slot pair and use neither arm.
   <!-- /cheap-tier -->
8. **Learn-verification (advisory)**: run `python3 "$TP_ROOT"/skills/_shared/verify_learn.py --range {default}...tp/{design-name} --json` (where `{default}` is the base branch — usually `master`). It reports `three-pillars-docs/**` lines (living **and** `completed-tp-designs/`) that still name a symbol or file this design **retired** (deleted/renamed in the diff) — the "learn ran ≠ docs match as-built" gap. Treat any hit as a propagation miss: fold the scrub into the step-7 doc updates. **Advisory only** — the helper always exits 0 and fails open; never block on it. Surface any remaining hits in the step-12 report (and, in `--auto`, append them to `decisions.md`). The three-dot range diffs merge-base→`tp/{design-name}`, surfacing *this design's* deletions, not the base side's.

   The same `verify_learn.py` run also surfaces **stale invariant-number citations** in the design's touched prose files (any file changed within the diff range that cites an `invariant #N` where N is not a live invariant number in `framework-check.sh`). This stale-cite check is framework repo only (needs `framework-check.sh`) and is skipped in user repos, where it reports nothing. These appear alongside the retired-symbol refs in the JSON output. Treat a stale-cite hit as an advisory repair prompt (cite a live invariant or drop the number); never block on it.

   Also run `python3 "$TP_ROOT"/skills/_shared/citation_liveness.py --repo . --remote --json` and fold any `DeadCite` or `StaleRow` hits into the step-7 doc updates. **Advisory only** — exits 0, fail-open offline; never block on it.

   8b. **Consumer-facing change (advisory)**: run `python3 "$TP_ROOT"/skills/_shared/consumer_facing_change.py check --range {default}...tp/{design-name}` (same three-dot range as above). It reports the watched commit-protocol doc sections this design changed. When `flagged`, propose one release-note line and one migration note naming the flagged `sections` — the protocol change is visible to consumer repos, so they need to hear about it. **`--auto`**: write both as a Decision Entry with `Confidence: Low` (needs operator review). Always exits 0 — never block on it.

9. **Scan for affected sibling designs**: Read all `design.md` files under `three-pillars-docs/tp-designs/` (excluding the current design). Match key concepts — new modules, changed interfaces, architecture decisions from `implementation-audit.md` or `detailed-design.md` — against each design's Scope and Entities sections. For each affected design, also check whether its declared dependencies include the current design — if so, note whether those dependency requirements are now satisfied. List affected designs with an explanation of what needs updating.

   When an affected sibling is an **archived** design whose documented behavior this design changed, propose the dated amendment per `skills/_shared/reconcile-protocol.md`. In `--auto`: apply the amendment and log to `decisions.md` with `Confidence` per `auto-mode.md` rules.
10. **Vision drift check (do not auto-propose vision edits)**: Compare what was actually built against `three-pillars-docs/vision.md`. Does the implementation contradict a stated principle or non-goal? Does it serve the stated problem in a way the vision didn't anticipate? If you find a genuine tension — not a stylistic mismatch — **flag it** to the user with a specific citation (which implementation detail, which vision bullet) and recommend `/tp-docs-update vision` as an explicit follow-up. **Do not propose vision edits directly from this skill.** The sticky-vision principle exists to prevent post-hoc rationalization: shipped features are not evidence the vision changed.
10b. **Run retro (this run's framework friction; protocol, consent and board contract in `skills/_shared/run-retro.md`).** `<design dir>` is the step-2 directory, `<scratch>` the run's scratch dir. It proposes and files; it never edits a skill. Fail-open: a non-zero exit logs one line and the skill goes on to step 11.
    - First, gate: run `python3 "$TP_ROOT"/skills/_shared/retro_gate.py --repo .`. On exit 1 (`retro.enabled` is not true), run `python3 "$TP_ROOT"/skills/_shared/run_retro.py note --design-dir <design dir> --title "skipped (retro.enabled off)"` and go to step 11, with nothing else from 10b.
    - `python3 "$TP_ROOT"/skills/_shared/run_retro.py known-items --repo . --out <scratch>/known-items.json`, then `python3 "$TP_ROOT"/skills/_shared/run_retro.py draft --design-dir <design dir> --known-items <scratch>/known-items.json`; it prints `review_needed`.
    - Only when `review_needed`: `python3 "$TP_ROOT"/skills/_shared/run_retro.py review-prompt --design-dir <design dir> --known-items <scratch>/known-items.json` prints a brief path. Run `Agent(subagent_type=agent_ref("tp-readonly-auditor"), model="opus")` on it and save the reply as `<scratch>/verdicts.md`. Otherwise skip the reviewer and drop `--verdicts`.
    - `python3 "$TP_ROOT"/skills/_shared/run_retro.py file --design-dir <design dir> --verdicts <scratch>/verdicts.md --board <automated_upgrades|none> --notion-skill <present|absent>`. Use `--board automated_upgrades` only when the repo's notion-ops config has an `automated_upgrades:` block, else `none`; `--notion-skill present` only when `notion-file-upgrade-request` is in the session's skill list. With no board it writes fallback seeds (the consumer-repo path) and prints each seed path it wrote or changed: stage exactly those in step 11, never a glob.
    - Board path (`file` printed an outbox with entries): interactive, show `retro-outbox.json` and ask once; on a decline run `python3 "$TP_ROOT"/skills/_shared/run_retro.py note --design-dir <design dir> --title declined`, post nothing and skip `record`. `--auto`: post, never prompt. Post one `/notion-file-upgrade-request --package <package> --type <Bug|Idea> --source-run <design-slug> --root-cause-group <text> --evidence <pointer>... --reviewer-verdict <accept|merge-with> --version <version> [--design <design>] [--rrsi-flag <flag> ...] [--recurrence <n>]` per `retro-outbox.json` entry (the skill's own doc in notion-ops-skills is the spec), its flags taken from that entry's `payload`: `--source-run` is the design slug, `--reviewer-verdict` is the word before the first `:` of the payload's reviewer verdict, `--evidence` and `--rrsi-flag` repeat once per list item (leave `--rrsi-flag` out when the list is empty). Each call replies one line, `filed: <action> <url>` or `not filed: <reason>` (normal when the teamspace has not enabled automated upgrades). Write the reply lines as `<scratch>/filed.json`, `[{slug, reply}]` with the entry's `slug` and the line verbatim (leave an error out: its entry stays in the outbox), then run `python3 "$TP_ROOT"/skills/_shared/run_retro.py record --design-dir <design dir> --filed <scratch>/filed.json`. `record` seeds each `not filed` entry on its own and prints `seeds`: stage exactly those in step 11.
11. **Commit the fragment** per `skills/_shared/commit-after-work.md`. Artifact paths to stage (include only those actually modified in steps 5–10b):
    - `three-pillars-docs/changes/{design-name}.md`, the only living-doc path (the guard refuses a shared living doc)
    - `.three-pillars/fragility-rules.json` (when step 7's fragility-class rule proposal was approved and `fragility_repo_rules.py add` ran)
    - `<design dir>/retro-findings.json` and `<design dir>/retro-outbox.json` (when step 10b wrote them), plus the exact seed paths `file` and `record` printed (new seeds and any seed that got an evidence line)
    - Legacy slug only, the docs its step-7 edits modified: `product_roadmap.md`, `architecture.md`, `known_issues.md`, `known_issues_resolved.md` (**move** a resolved entry there verbatim), `known_issues_low.md` and any `known_issues_low_<n>.md` part (a promoted Low **moves** back into `known_issues.md` in the same commit), and the rollover archives `architecture_archive.md` and `product_roadmap_archive.md` (when the rollover moved entries)
    Before the commit, run `python3 "$TP_ROOT"/skills/_shared/cache_measure.py --append three-pillars-docs/tp-designs/{design-name}/decisions.md` for every weight class, light included: it appends one `[cache]` line, or `cache: no transcripts`. Stage `decisions.md` with the doc updates.
    Do NOT stage `three-pillars-docs/vision.md` — this skill never auto-edits vision. Commit message: `Learn: {design-name} design`.
12. **Report**: Summarize what was updated, what designs are affected, any vision tensions flagged, and suggest `/tp-design-complete {design-name}` as the next step.

## Rules
- Follow `skills/_shared/propose-doc-edits.md` for all doc updates.
- Works on both active (`three-pillars-docs/tp-designs/`) and archived (`three-pillars-docs/completed-tp-designs/`) designs.
- **Never auto-edit `three-pillars-docs/vision.md`.** Flag tensions, recommend `/tp-docs-update vision`, let the user decide.

## Auto Mode

`/tp-design-learn --auto` follows **Shape B (Generator)** per `skills/_shared/auto-mode.md` — it derives the inventory, Current Focus and architecture/known-issues/roadmap lines from the design's artifacts without per-edit confirmation.

**Never auto-edits `vision.md`.**

Behavior in `--auto`:

- **Skip user-confirmation in steps 5, 6, and 7.** Write the proposed inventory row (step 5), Current Focus (step 6) and architecture / known-issues / roadmap lines (step 7) straight into the fragment. No "show diff and wait" — just write.
- **Pending token:** `Completion PR pending` goes in the Design Inventory status cell (placement per `skills/_shared/living-doc-format.md`); Recent completions uses `Done — {pr}`.
- **Log every diff applied as a Decision Entry in `decisions.md`** — one entry per diff, with `Confidence: High | Medium | Low` and reasoning. Use the schema-v1 init/append protocol referenced inline in `skills/_shared/auto-mode.md` (canonical snippet — do not reimplement). The skill name prefix is `[tp-design-learn]`.
- **Step 10 (vision drift check): log tension to `decisions.md` and continue.** If you detect a genuine tension between the implementation and `three-pillars-docs/vision.md`, append a Decision Entry describing the specific implementation detail and vision bullet in tension, with `Confidence: Low` (the user must review). **Do not propose, draft, or apply any edit to `vision.md`.** The bolded contract above (`` **Never auto-edits `vision.md`.** ``) is load-bearing: it preserves the sticky-vision principle even when no human is in the loop.
A known issue you file here uses a placeholder ID, numbered later (see `skills/_shared/issue-id-placeholders.md`).

- **Step 10b (retro) still runs when `retro.enabled` is true.** Under a configured board it posts without asking, so a decline never occurs; the CLI logs each id.
- **Step 11 (commit) still runs.** Stage only the fragment `three-pillars-docs/changes/{design-name}.md`, `decisions.md`, `retro-findings.json`, `retro-outbox.json` and the exact seed paths `file` and `record` printed (a legacy slug also its modified `product_roadmap.md`, `architecture.md`, `known_issues.md`, `known_issues_resolved.md`, `architecture_archive.md`, `product_roadmap_archive.md`) — never `vision.md`. Commit message stays `Learn: {design-name} design`.
- **Lock conflict** is BLOCKED in `--auto`, not a prompt — append a BLOCKED Decision Entry and exit non-zero per `skills/_shared/auto-mode.md` Rule 5.

Shape B with logging: per `design-pipeline-auto-mode/design.md` Vision alignment, the "Silent mutation" tension is accepted because `decisions.md` captures every diff and the outcome PR is human-reviewed.
