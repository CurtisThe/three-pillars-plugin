# tp-merge-from-main — worktree-aware base-sync + living-doc conflict resolution

When parallel designs run in their own worktrees, the base branch moves under them and a
merge conflict on the shared living docs (`known_issues.md`, `product_roadmap.md`,
`architecture.md`, `vision.md`) is the *expected* case at `/tp-design-complete` time. Manual
resolution is slow and — as the parent spike proved on real PR-#28 history — a silent
**content-drop** risk: a careful human merge dropped a known-issue entry outright.

`/tp-merge-from-main` merges the base into the design's worktree branch and auto-resolves only the
**provably-mechanical** living-doc conflict classes behind an independent zero-drop verifier.
Everything semantic is left as conflict markers for the human. It is the conflict-handling
step the merge-back flow never had; it composes with `/tp-pr-iterate` for the post-merge
re-review loop.

> **Base-sync, not land.** `/tp-merge-from-main` is the *reversible* base-into-branch
> operation (it merges `{base}` into the design branch and re-pushes the branch). It is
> **not** the irreversible `gh pr merge` that lands the PR to `{default}` — that is the
> separate `/tp-merge` land skill, which enforces the deterministic merge gate (including
> the human-approval predicate) before crossing the boundary. Keep them distinct: this
> skill syncs the base in; `/tp-merge` lands the PR out.

**The boundary** (from the `worktree-merge-conflict-flow` spike, verdict GO; log classes un-gated by `basesync-prepend-log`):
- **AUTO-SAFE** (auto-resolved + verified): `design-inventory-row-merge`, `log-entry-insertion` (dated entries and plain-date bullets `- YYYY-MM-DD — …`), `append-only-log`, `decision-entry-insertion`, plus the newer classes `keyed-heading-insertion`, `keyed-row-insertion` (slug-keyed table rows both sides append over an empty base), `shaped-line-merge` (ID- or slug-keyed rows and single-line log bullets over a non-empty base, never prose; plain-date log bullets — a base bullet a side removed is dropped only when the file-level move proof shows it moved into that side's archive), the design-dir `decisions.md` tail union, `last-updated-preamble` (each side exactly one dated `*Last updated: YYYY-MM-DD …*` line and nothing else), `low-count-line` (the `N Low issues →` count line in `known_issues.md`: ours + theirs − base, checked against the merged Low parts) and `regenerate`, plus `hard-cap-rollover` (a live doc the merge pushed past its hard cap is rolled by `skills/_shared/doc_rollover.py` and re-verified together with its archive, else deferred). A sync resolved through `regenerate` (a declared generated file such as `plugin.json`) still **re-requests review**: that file is outside the approval-carry allowlist (`base_sync_cert._cond3_allowlist` admits only the living-doc set), so the approval does not carry.
- **GATED** (classified, always deferred — `classify.GATED`): `id-renumber-collision`, withheld since round 20 because its renumber sees only the one conflicted file (not the IDs other living docs cite or have already spent) and it renumbers the base branch's already-landed entry.
- **ALWAYS-HUMAN** (deferred): `preamble` (any preamble hunk that is not one such dated `*Last updated:*` line per side — those are AUTO-SAFE above), `current-focus-reprioritization`, `generic-prose`.

**The resolver rule (`skills/tp-merge-from-main/scripts/resolve_totality.py`).** *A mechanical resolver never discards a line it does not understand — it preserves every input line, or it defers.* Stated over LINES, not atoms: the verifier can only see a lost line if that line parses as an atom, so an atom-level rule would leave ordinary prose free to vanish under a RESOLVED verdict — a silent content loss on the one lane that certifies byte-safety without a human. Three consequences at the boundary above: a hunk mixing an AUTO-SAFE shape with foreign content is **not** that class (every AUTO-SAFE class carries a purity predicate: the two insertion classes each require every side to START at an entry of the class and open no foreign section — a heading in any form, indented ATX and setext included, is foreign — `append-only-log` holds two differing tails to the log-insertion predicate, those three need the first line after the region to start an entry or be EOF whenever they emit both sides' lines, and those three hold every line of each inserted block (of each differing `append-only-log` tail that is not whitespace only) to an allowlist (`scripts/line_shapes.py`): the class's entry start, or a line that — read past its leading whitespace and list markers — is not heading-shaped at any step of that reading (an ATX `#`–`######` or a bare `---` / `===` underline, at any indentation, since a heading nested in a list item sits four or more columns in; an underline shape directly below a blank line of the same side is admitted, since no paragraph is open there for it to underline, and one on a side's first line is refused), does not begin with `<` (HTML block), three or more `` ` `` or `~` (code fence), `>` (block quote) or `$$` (math block) and is not a link or footnote definition (`]:`), with a carriage return allowed only as a line's last character — it refuses by first token, not by parsing, so a balanced fence, a one-line `<!-- … -->` comment or a `> ` reply inside an inserted entry defers the file although it cannot swallow anything (27 of the repository's 1814 decision entries, 1.5%, carry such a line); its heading and block-opener tests read only a line's START (past indentation and list markers), so an unclosed inline raw HTML element later in a line (`… wrap long evidence in <details> blocks`, an unclosed `<s>`, `<b>` or `<a href>`) is admitted: an accepted residual that can visually wrap the other side's following entry on GitHub's renderer, left unrefused because mid-line `<placeholder>` text is common; and the inventory arm admits table lines only, and only as rows of ONE table: no blank or whitespace-only line, no line of pipes only and no carriage return inside a line on either side, no header or `| --- |` except one identical frame both sides open with, and no row appended directly above a delimiter row or above a line with a carriage return inside it — so a keep-both merge never moves a line from one side's entry to the other's, nor puts one side's entry inside an HTML block, code fence or heading section the other side opened, nor moves a row into another table or out of its table); a hunk whose sides contain a conflict marker is not well-formed input for any class and defers; and any mechanical result that does not account for its own input lines is discarded in favour of a deferral, whatever the resolver believed. The lane is therefore **narrower** than the class list alone implies — a mixed hunk costs a human resolve rather than silently losing a line.

**The index is the oracle for the text parse (`scripts/stage_oracle.py`).** All three rules above read the conflict TEXT, and the text is the one thing that can lie: git's marker grammar is ordinary markdown (`|||||||` is a table row of empty cells, `=======` a setext underline), so any rule that reconstructs a region's structure by shape-matching can be defeated by content that imitates it — and a region cut in the wrong place routes real content onto a side no resolver reads. The merge **index** carries the same structure with no such ambiguity: stage 1 is the base blob, stage 2 ours, stage 3 theirs, marker-free and authoritative. So before the driver accepts any mechanical result, it checks the parse against the stages — every line the parse put on the ours side must be a line of stage 2, and so on — and **defers the file untouched on any disagreement**. This is a validation gate only: it changes no bytes, and the RME-certified `resolve_conflict_bytes` path is untouched. It runs where the index exists (`merge_driver.resolve_living_doc`); callers without one (the `resolve.py` CLI, unit tests on synthetic blobs) cannot run it and keep only the three text-side rules.

**Markers are bound to `git merge-file`'s own labels (round 17).** The byte path (`skills/_shared/auto_safe_resolution.py`) runs `merge-file` with per-call nonce labels that no input contains, and the parse accepts only marker lines EQUAL to those labelled markers — so a document that quotes conflict syntax, or a content line that merely begins `>>>>>>>`, stays content instead of being read as a region. The parse must also find exactly as many regions as `merge-file`'s exit status reports, or the file defers. Unlabelled callers (the CLI, synthetic-blob tests) still use the prefix scan.

`log-entry-insertion` is the real base-sync shape for newest-first ADR logs (architecture.md's `## History`): `git merge-file --diff3` minimizes the conflict to an **empty base** between two divergent insertion blocks, so detection keys off empty-base (⇒ no deletions) **and** both sides being bold-lead log bullets (`- **YYYY-MM-DD** —` or `- **`slug`** —`) — keep-both, zero-drop, fail-closed on any deletion or foreign structure. Whole entries both blocks open or close with (two archives rolling the same History) are kept once; a shared entry between unshared ones defers. (The classifier's `GATED` lever, empty after `basesync-prepend-log` un-gated the log classes, holds `id-renumber-collision` since round 20 — see the boundary above.)

**Approval-carry consequence.** When a base-sync is **fully AUTO-SAFE** (every conflict mechanical, certified byte-for-byte), the `approval-survives-safe-base-sync` carry keeps your existing PR approval + review proof **current** — no re-approval. A sync that **hand-resolves** any ALWAYS-HUMAN hunk cannot be certified byte-for-byte mechanical (the hand-edit is a real content change). **Exception — living-doc hand-resolution carry (default-ON within an already-carry-enabled repo):** the `livingdoc-handres-preserves-approval` relaxed certifier still carries the approval across a base-sync whose only files differing from a clean mechanical merge are **carry-set living-doc `.md`s** proven **code-unchanged** (carry-set predicate + cond4 containment + zero-drop, byte-*reproduction* relaxed) — so a hand-resolved living-doc hunk no longer forces a re-approval; only a hand-resolved **code** (non-carry) hunk, or a living-doc hand-res that **drops** a content atom, still **stales** the approval and you must re-approve. Serial fleet PRs sharing a living doc do **not** each re-approve by default — verify the merge-tree **empirically** (`--dry-run`) before assuming a re-approval tax: a later PR can sync cleanly when its merge-base already holds the earlier PR's entry (different insertion line → no collision). See `skills/_shared/human-approval-howto.md` §"Does a base-sync cost me a re-approval?".

**Resolution boundary.** The driver's resolver behind the zero-drop verifier is the one supported way an agent resolves a living-doc conflict. An agent never hand-rolls conflict-marker parsing (a regex or script over the marker lines) and never rewrites a conflicted living doc in place. Whatever the driver defers stays deferred to the human: the agent reports it (step 4) and stops, without attempting a resolution. The one exception is a `resolved` `base-sync-hunk` ruling applied from the zero-drop VERIFIED proposal as step 4 says.

## Arguments

- `{design-name}` (required) — must match an existing directory under `three-pillars-docs/tp-designs/` and an active `tp/{design-name}` worktree branch.
- `--base <branch>` (optional, default the repo's resolved default branch — see `skills/_shared/default_branch.py`) — the base branch to merge in (uses `origin/<branch>`).

- **Matchable commands**: run plain `git <verb>` in the design's worktree (the cwd), `git -C <dir> …` only for a second checkout, and tests from the repo root, never `cd <dir> && …`; take any second checkout (a compare against the base) with `python3 "$TP_ROOT"/skills/_shared/scratch_worktree.py add <name> <ref>`, not a hand-built worktree (`skills/_shared/matchable-commands.md`).
- `--no-push` (optional) — resolve and re-run tests, but stop before pushing (human pushes).
- `--force-takeover` (optional) — claim the design lock per `skills/_shared/collaboration.md`.
- `--cheap-tier[=ab]` | `--no-cheap-tier` (optional, deprecated) — both change nothing: the step-4 splice proposal (shown; applied only by a `resolved` `apply-proposal` ruling, step 4) per `skills/_shared/cheap-dispatch.md` runs in every invocation. Resolve `<mode>` once with `python3 "$TP_ROOT"/skills/_shared/cheap_tier_default.py --root . [--cheap-tier[=ab]|--no-cheap-tier]`: its stdout is always `on` (a set `cheap_tier.default_run_flag` is deprecated too; each deprecated input prints one `deprecated:` line, and a dropped config prints its one-line warning). `<mode>` is `on`; step 8 forwards bare `--cheap-tier` to `/tp-post-merge`.

## Steps

0. **Run first-run preflight** per skills/_shared/first-run.md.

0a. **Run cwd preflight** per `skills/_shared/cwd-preflight.md`: `python3 "$TP_ROOT"/skills/_shared/cwd_preflight.py {design-name}`. Exit 3 → stop and show the `cd` fix. Exit 0 → continue.

1. **Validate `{design-name}`** per `skills/_shared/validate-name.md` (must match `[a-z0-9-]+`; reject `/`, `..`, spaces). Then run the collaboration preflight per `skills/_shared/collaboration.md` with `phase: "implement"` (the merge-back rewrites tracked files like an implementation step; `phase` is constrained to the schema's fixed set, which has no `merge` value). `/tp-merge-from-main` rewrites tracked files and pushes, so the lock must be held by the rightful owner. Honor `--force-takeover` if passed.

2. **Fetch the base**: `git fetch origin <base>` (default the repo's resolved default branch — see `skills/_shared/default_branch.py`). The base ref being fetched here is synced from the **seat** — the base checkout / worktree host that hosts the design worktrees. If you are unsure which checkout is the seat, run `seat_resolve.sh --where` from the repo root; this skill already runs inside the design's own worktree, so the seat is the sibling base checkout. See `skills/_shared/topology.md` for the canonical seat and worktree layout definitions.

2b. **Number placeholder known-issue IDs** before the driver merges: `python3 "$TP_ROOT"/skills/_shared/number_issues.py --base <base> --commit` (a no-op when nothing is a `<S>-new-<slug>` placeholder; see `skills/_shared/issue-id-placeholders.md`). It numbers against `origin/<base>` as fetched in step 2 (the local `<base>` only when no remote-tracking ref exists). **Under `--dry-run`, drop `--commit`**: the CLI then runs in plan-only mode, printing the plan as JSON and writing and committing nothing.

3. **Run the merge driver** from the repo root of the design worktree:
   ```bash
   python3 "$TP_ROOT"/skills/tp-merge-from-main/scripts/merge_driver.py "$(git rev-parse --show-toplevel)" "origin/<base>"
   ```
   The driver:
   - runs `git merge --no-commit --no-ff origin/<base>` inside the worktree;
   - for each conflicted **living-doc** file, reconstructs `(base, ours, theirs)` from the index stages, then runs `classify → resolve → verify` **per hunk**;
   - applies the staging policy and prints a JSON report with three per-file outcomes:
     - **auto-resolved** — every hunk mechanical, verifier zero-drop, no markers → written + `git add`ed.
     - **partially-resolved** — mechanical hunks pre-resolved in place, semantic hunks left as markers (file *not* staged). This is the common case: a real living-doc conflict usually also touches prose that is semantic (a lone dated `*Last updated:*` line per side is AUTO-SAFE).
     - **deferred** — all-semantic, a verifier-flagged drop, a **still-conflicted blob the verifier could not clear**, an **unverifiable shape**, an add/delete conflict, or any non-living-doc (code) conflict → left untouched.

     > The verifier removes **no** line before digesting a `### [tag] title` body — conflict markers included — because every version of that strip eventually hid real content from a signature (see `verify_atoms.py`'s header). So a `decisions.md` whose remaining markers land *inside* an entry's body verifies as a drop even though every entry is present, and the file is **deferred rather than partially-resolved**: same "a human must finish this file", one less convenience. The report reads *"could not verify a still-conflicted blob (merge markers remain) AND {n} atom(s) appear missing from it — the markers may account for some or all, so check for lost content"*: **both** facts, because the driver cannot tell them apart — `_still_conflicted` is shape-only, so prose that merely *quotes* conflict syntax is indistinguishable from a real region. Read it as "the markers are the likely explanation, but confirm no content is missing." A blob with **no** markers at all reports the drop unhedged (*"verifier flagged content drop"*). Docs without `### [tag]` entries (`known_issues.md`, `product_roadmap.md`) are unaffected: their atoms are per-line.
   - exit `0` = fully resolved/clean; exit `2` = human attention needed; exit **`3` = `git merge` itself failed for a non-conflict reason** (unknown base ref, dirty worktree, a merge already in progress) — nothing was merged and nothing was attempted, so the report carries `merge_failed: true` and a `merge_error`. `3` is distinct from `2` because there is no conflict to finish: fix the repo state and re-run. (Before this, that case fell through an empty file loop and exited `0` — indistinguishable from a clean merge.)

   `verify.py` run standalone takes `<ours> <theirs> <resolved> [--base PATH] [--mechanical-applied]` (three-way with `--base`: a base atom one side changed in place while the other left it as base is excused) and exits `0` = ZERO-DROP, `1` = drops detected, **`2` = UNVERIFIABLE** — it parsed zero atoms from ours∪theirs on a file the resolver had actually mechanically resolved, so this file's shape is unknown to the verifier and "no drops" would mean "nothing examined" — and **`3` = usage or I/O error** (bad invocation, or an input path that could not be read/decoded). `3` exists because argparse's own usage exit is `2`, which would otherwise be indistinguishable from UNVERIFIABLE; a `3` means the verifier never ran, not that the merge is unsafe. Pass `--mechanical-applied` only when a mechanical resolution really was applied; without it a deferred or hand-resolved prose file is not blocked.

4. **Surface what the human must finish.** From the report's `partially_resolved` + `deferred` lists, tell the user exactly which files still carry conflict markers and which hunks remain (e.g. "`product_roadmap.md`: preamble + current-focus need you"). **Never stage or commit a file that still contains conflict markers** — the driver enforces this; do not work around it.
Each deferred or partially-resolved living-doc file outside the pillar docs (`PILLAR_DOCS` in `skills/_shared/finalizer_ruling.py`) is one `base-sync-hunk` question per `skills/_shared/escalation.md`, naming the file and the deferred hunk's heading or first changed line, raised after the cheap-tier proposal below with the proposal's scratch path in its `context` (or `none verified`) and the options `apply-proposal` (only when a zero-drop VERIFIED proposal exists) and `leave-for-human`; Fable rules it first. On `resolved` with `apply-proposal` re-run `python3 "$TP_ROOT"/skills/_shared/cheap_oracle_run.py check --slot base_sync_splice --artifact <A.json> --ctx <C.json>` on the proposal (must give `accept`; its `zero_drop` check also refuses any line not in ours + theirs + base), copy the proposal over the file (never hand-edit marker lines, never write text from the ruling), run `verify.py <ours> <theirs> <resolved> --base <base>` (must exit 0) and `file_size_guard.py` on it, stage it, and list it as `fable-applied (ruling <id>)` in the step-7 merge note. With `leave-for-human` (returned as `escalate`) or on `escalate` (including `low` confidence), the hunk waits for the human and the card carries Fable's recommendation. With no zero-drop VERIFIED proposal, skip Fable; with none, or when an `apply-proposal` re-check is not `accept` or exits non-zero, run `python3 "$TP_ROOT"/skills/_shared/finalizer_cli.py escalate --stop <stop> --reason no-proposal --decisions <d>/decisions.md --scope <slug>` so the park gets a ruling file and an `awaiting-operator` card, and the hunk waits for the human. A pillar-doc hunk skips Fable: raise its question and run `python3 "$TP_ROOT"/skills/_shared/finalizer_cli.py escalate --stop <stop> --reason pillar-doc --decisions <d>/decisions.md --scope <slug>` so it still gets a ruling file and an `awaiting-operator` card, and it waits for the human.
Offer (f): if a deferred conflicted path is a lockfile, run `python3 "$TP_ROOT"/skills/tp-merge-from-main/scripts/generator_catalog.py detect --repo . --only <deferred paths> --json` and follow offer (f) in `skills/_shared/consumer-offers.md` (interactive: show the match, accept or decline; `--auto`: log a suggestion, write nothing).

   <!-- cheap-tier:base_sync_splice -->
   **Cheap-tier splice proposal (the loop is `skills/_shared/cheap-dispatch.md`).** Run it before the wait below, while the index still holds stages 2 and 3 (in `--dry-run` too). For each living-doc file the report lists as `partially_resolved` or `deferred`, run `python3 "$TP_ROOT"/skills/_shared/cheap_tier_cli.py spec --slot base_sync_splice --root . --cheap-tier <mode>`; a null rung changes nothing here. Otherwise write the file's ours and theirs (`git show :2:<file>`, `git show :3:<file>`) to scratch files, snapshot the worktree with `python3 "$TP_ROOT"/skills/_shared/live_tree_guard.py snapshot --root . --store <S>` (`<S>` a fresh scratch dir), and spawn `Agent(subagent_type=<spec.agent_ref>, model=<spec.model>, …)` to write one scratch file: the proposed `resolved` text for that file. Then run `python3 "$TP_ROOT"/skills/_shared/live_tree_guard.py check --root . --store <S> --exclude <scratch dir>`: `ok: false` (`drafter-wrote-live-tree`) means the drafter wrote the worktree. It has put back only those paths, conflict stages included, and the proposal drops with that reason.
   Check it with the `zero_drop` oracle: `python3 "$TP_ROOT"/skills/_shared/cheap_oracle_run.py check --slot base_sync_splice --artifact <A.json> --ctx <C.json>` (artifact `resolved`; ctx `ours_path`, `theirs_path`, optional `base_path`). Only on `accept` (zero-drop VERIFIED) show it next to that file's deferral as `cheap-tier proposal (zero-drop VERIFIED, not applied)`. Anything else drops the proposal and names the drop and its reason in the report. The proposal is applied only by a `resolved` `apply-proposal` ruling (above); until then do not write it into the worktree, stage it or commit it. `verify.py` misses semantic mis-merges, so without that ruling the human still resolves the file. Record each attempt per the dispatch doc; under `ab`, run its pure-slot pair and show neither arm.
   <!-- /cheap-tier -->

   Wait for the human to finish the deferred hunks (an agent reports and stops here; see the Resolution boundary) before continuing (in `--dry-run`, stop here and `git merge --abort`).

5. **Re-run the project test suite** in the worktree once all conflicts are resolved (auto + human). If tests fail, stop and surface the failure — do not push.

6. **Commit the merge** once the tree is conflict-free and green: `git commit --no-edit` (preserves the merge message). With `--dry-run` or `--no-push`, stop before this.
   - **Roll the doc to its cap in the same commit**: for each living doc you wrote, run `python3 "$TP_ROOT"/skills/_shared/doc_rollover.py --doc <repo-relative doc>` and keep the condensed form per `skills/_shared/living-doc-format.md` §Condensed shape and caps (one bullet or row per item, history to the archive); stage the doc's archive in the same commit.

6.4. **Record the changed-tests run for the new head.** Step 5's test run was on the uncommitted merge, so once the merge commit exists, record the fragility run for it, in the design worktree. This is what the `fragility_clear` merge predicate (see `skills/_shared/test-fragility.md`) reads for this head after the push in step 7, so a later `/tp-merge` does not have to take it:
   ```bash
   python3 "$TP_ROOT"/skills/_shared/changed_tests_runs.py record --root "$(git rev-parse --show-toplevel)" --base "origin/<base>" --head "$(git rev-parse HEAD)"
   ```
   Exit 0 = pass, 1 = a changed test failed its repeated runs, 2 = unverified or not written. **Fail-open**: report a non-zero exit, never block the merge on it, because the predicate reads the record itself and `/tp-merge` records again when it is missing. The step follows step 6, so it is skipped under `--dry-run` and `--no-push`.

6.5. **Closeout check (warn, never block)**: before pushing, run `python3 "$TP_ROOT"/skills/_shared/detect_unarchived.py --repo . --slugs-only` and check whether `{design-name}` appears — i.e., its `three-pillars-docs/tp-designs/{design-name}/` dir carries implementation evidence (`implementation-audit.md` / `spike-results.md`) but has **not** been archived to `completed-tp-designs/`. If it does, **warn** (do not block): the design has shipped but is not closed out — run `/tp-design-learn {design-name}` (or `/tp-spike-learn`) **then** `/tp-design-complete {design-name}` before the human merges, or the framework's CI check will hard-fail once the dir lands on `{default}` unarchived. `/tp-merge-from-main` is a conflict resolver, **not** a closeout gate — it surfaces the gap and proceeds; the CI check is the hard backstop, this is only the soft in-context nudge. **Fail-open**: a detector error is ignored (the helper always exits 0).

6.6. **Readiness advisory (warn-never-block)**: call `merge_gate.merge_readiness_warning(pr_url)` (from `skills/tp-merge-from-main/scripts/merge_gate.py`). If the return value is non-None, **print it as a WARNING** and **proceed** — never block. This mirrors the step-6.5 `detect_unarchived` warn-never-block contract: `/tp-merge-from-main` is a conflict resolver, not a readiness gate. The warning names the failing readiness sub-state from `classify_readiness` (`copilot-errored`, `review-stale`, `awaiting-copilot`, `unreviewed`) so the human can decide whether to remediate before merging. It is distinct from the blocking step-6.7 sync gate. **Fail-open**: a detector error (fail to fetch, network issue) returns `None` and is silently ignored — a failing readiness check must never nag or block.

6.7. **Sync gate (blocking, fail-closed)**: before pushing, check the push-readiness of the base-sync itself:
   ```bash
   python3 "$TP_ROOT"/skills/tp-merge-from-main/scripts/sync_gate.py --repo "$(git rev-parse --show-toplevel)" --base "origin/<base>"
   ```
   It checks, on the local worktree, only what a base-sync can decide before it pushes: **merge-concluded** (no unmerged paths, no merge in progress), **tracked-tree-clean** (the head to push is the tree step 5 tested and step 6 committed), **base-is-ancestor** (`origin/<base>` is an ancestor of HEAD, the local fact that clears the remote `mergeable` once pushed) and **no-leftover-markers** (no `<<<<<<<` / `>>>>>>>` line the merge commit adds relative to both parents). Exit **0** = PASS, proceed to step 7. Exit **1** (a check failed) or **2** (the gate could not run: bad base ref, not a git repo) **refuses the push** — fix what it names and re-run. Together with the merge driver's exit code and verifier (step 3) and the green suite (step 5), this is the whole push criterion of a base-sync. It needs no `gh`, no network and no seat.

   **Why not the land gate here.** The land gate's predicates (`mergeable`, `review_proof_on_head`, `human_approved`, `copilot_on_head`, `checks_success`, `ci_local_stamp`, `fragility_clear`) describe the **remote head** or landing state. Before this push the remote head is still the conflicting one and the merge commit does not exist on the remote, so none of them can hold: `mergeable` reads `CONFLICTING` because of the very conflict this sync clears. Running the land gate here blocked the push that would satisfy it (`merge-from-main-gate-circularity`). The land gate is enforced, unchanged, by `/tp-merge` before `gh pr merge`; step 7a prints its state after the push.

7. **Push only when green**, then **update the PR**: push the branch, refresh the PR body with a short merge note (base SHA merged, which files auto-resolved, which the human finished), and **re-request review** so branch protection re-triggers — compose with `/tp-pr-iterate` / `pr-fix-targeting-and-auto-review` for the Copilot loop. Pushing happens only here, and only on a green suite and a passing step-6.7 sync gate.

   **Producer breadcrumb (audit-only, ZERO gate authority)**: when the merge driver's report shows the sync was **fully auto-resolved** (no `partially_resolved` / `deferred` entries — every conflicted living-doc file resolved mechanically), post the `basesync-cert.v1` comment via `cert_comment.format_cert_comment(pre_sha, post_sha, resolved_classes)` + `cert_comment.post_cert_comment(pr_url, body)` (`skills/tp-merge-from-main/scripts/cert_comment.py`) — the pre/post merge SHAs and the resolved conflict classes (e.g. `design-inventory-row-merge`). **Failure to post is logged and ignored** — `post_cert_comment` is best-effort and never raises. **The deterministic gate NEVER reads this comment**: the `approval-survives-safe-base-sync` carry re-derives certified links from git objects alone (the first-parent walk + per-link RME re-proof), never from a PR comment — see `three-pillars-docs/completed-tp-designs/approval-survives-safe-base-sync/detailed-design.md` (Producer breadcrumb section). **Deferred living-doc hand-resolutions (`livingdoc-handres-preserves-approval`)**: when the sync instead **deferred ≥1 living-doc file** to the human (the deferred set the driver already tracks, filtered through `living_doc_carry.is_living_doc_carry_path`), post `cert_comment.format_handres_cert_comment(pre_sha, post_sha, handres_files)` + `cert_comment.post_cert_comment(pr_url, body)` — same audit-only, **ZERO gate authority** boundary: the deterministic gate re-derives the carried K from git objects (the first-parent walk + relaxed per-link re-proof, `is_living_doc_carry_path` + cond4 + zero-drop) and **never reads this comment**, so a forged/absent/wrong-author copy changes no verdict.

   The native-review approval path (`review-as-human-approval`) is **self-cleaning for real content changes**: a review carries an immutable server-set `commit_id`, so a genuine content change makes `commit_id != head` and the gate fails closed automatically at evaluation time. The `approval-survives-safe-base-sync` carry is the one narrow, opt-in exception: it extends an approval's currency **only** across a chain of *certified mechanical base-sync merges* — each link independently re-proven from git objects (merge shape, allowlist, byte-equality outside the conflict set, resolver byte-reproduction), never trusted from a comment or config claim. A real (non-mechanical) content change is never certified, so the gate still fails closed exactly as before — the carry narrows **when** self-cleaning fires, it never weakens it. No strip hook is needed — the gate's currency re-check at the `/tp-merge` land gate is the fail-closed backstop (the step-7a readout shows the same re-check, advisory).

   **Operational precondition (full clone)**: the carry's chain walk requires a full (non-shallow) clone to re-derive certified links. On a shallow clone the guard reports a **distinct INDETERMINATE detail** ("shallow/incomplete history — cannot walk chain; carry requires a full clone") rather than a verdict indistinguishable from "no certified chain" — a documented implementation precondition, not a soundness gap (the guard fails closed either way).

7a. **Land-gate readout (advisory, after the push; warn-never-block)**: once step 7 has pushed, run the deterministic land gate so the human sees what landing still needs. **Dispatch-from-seat invocation** (keeps the base-sync approval carry visible in the readout — see below):
   ```bash
   SEAT="$(bash "$TP_ROOT"/skills/_shared/seat_resolve.sh --where)"
   if [ -n "$SEAT" ] && [ "$SEAT" != "NONE" ] && [ -f "$SEAT"/skills/_shared/resolve_root.sh ]; then
     TP_SEAT_ROOT="$(bash "$SEAT"/skills/_shared/resolve_root.sh --skill-dir "$SEAT"/skills/tp-merge-from-main)"
   else
     TP_SEAT_ROOT="$TP_ROOT"
   fi
   python3 "$TP_SEAT_ROOT"/skills/tp-merge-from-main/scripts/gate_cli.py --repo "$(git rev-parse --show-toplevel)" <pr_url>
   ```
   **Existence-guarded hop 2**: on a consumer repo the seat (the base checkout)
   does not contain the framework code (`"$SEAT"/skills/_shared/resolve_root.sh`
   does not exist there — only the dev repo is its own seat) — the guard falls
   back to the naive `$TP_SEAT_ROOT="$TP_ROOT"` automatically instead of hop 2
   failing loud and leaving the agent to improvise. This fallback is the
   documented-safe path (see the note below): the independent-oracle guard
   still fails CLOSED, just without the base-sync approval-carry capability.
   Or equivalently call `merge_gate.merge_gate_blocking(pr_url, repo_root=<worktree toplevel>)` from `skills/tp-merge-from-main/scripts/merge_gate.py`, loaded FROM the seat's copy. **Print the verdict and the blocking predicates, then proceed — whatever the exit code** (0 = PASS, 1 = FAIL, 2 = INDETERMINATE). On a fresh sync the expected blockers are the head-bound ones (`human_approved` unless a certified base-sync carry holds, `review_proof_on_head`, `ci_local_stamp`); `mergeable` may read `UNKNOWN` for a short while after a push while GitHub recomputes it — say so, do not retry in a loop. **Fail-open**: a gate error is reported, never blocks. The readout is informational only: `/tp-merge` re-evaluates the same gate, fail-closed, before it lands anything. The gate output always shows the label `mechanical predicates hold — semantics UNVERIFIED — your review is the only semantic check`.

   **Why the two-hop `$TP_SEAT_ROOT` resolution, not `$TP_ROOT` directly**: this skill already runs with cwd inside the design worktree, and the step-0 bootstrap's `$TP_ROOT` resolves relative to whatever checkout loaded the code — naively, that is the worktree under verification, not the seat. The approval-survives-safe-base-sync carry's independent-oracle guard (`base_sync_cert.oracle_independent`) is DISJOINT-CODE-gated: it checks where the *executing* gate code physically lives, and a worktree-resolved `$TP_ROOT`/`$TP_SEAT_ROOT` is **detected and refused** by that guard (an "unknown-worktree" / provenance-indeterminate refusal), not silently trusted. `seat_resolve.sh --where` (repo-global via `git worktree list --porcelain`, prints the seat path or `NONE`) plus `resolve_root.sh --skill-dir "$SEAT"/skills/tp-merge-from-main` (probe-2 grandparent, anchored at the SEAT's own skill directory — **not** the worktree's, and **not** probe-4's cwd-derived dev-checkout fallback) is the concrete, non-circular recipe that resolves the seat's code root from the worktree cwd. Skipping this note and running the naive `$TP_ROOT` invocation does not produce an unsound certificate — the guard fails CLOSED — but it silently loses the carry capability: an otherwise-valid base-sync-carried approval reports INDETERMINATE instead of PASS. `--repo "$(git rev-parse --show-toplevel)"` supplies the SUBJECT repo (the worktree) explicitly, independent of which checkout's code is executing.

   Predicates in the readout (the full list and their config switches are in `/tp-merge`'s SKILL.md):
   - **threads_resolved**: all review threads resolved (fail-closed: fetch failure → INDETERMINATE, not PASS)
   - **mergeable**: PR is in MERGEABLE state (CONFLICTING → FAIL; UNKNOWN → INDETERMINATE)
   - **checks_success**: all CI checks settled and concluded SUCCESS (empty rollup → INDETERMINATE, not PASS; INFRA_BLOCK → INDETERMINATE)
   - **copilot_on_head**: Copilot has reviewed the current head SHA (not reviewed → INDETERMINATE, not PASS)
   - **human_approved**: a current APPROVED human review from a non-automation human is present on the head SHA — enforced transparently via `evaluate_gate`'s `pred_human_approved` (no code edit here: `evaluate_gate` carries the fifth predicate when `review.require_human_approval` is true, the strict default). Absent/stale/automation-authored review → INDETERMINATE (never FAIL). See `skills/_shared/human-approval-howto.md` for how to authorize. The irreversible `gh pr merge` land step lives in the separate `/tp-merge` skill, which enforces this gate at the boundary.
   - **ci_local_stamp**: a fresh local-CI green stamp keyed to the head SHA, when the repo declares `ci.gate_command` (a fresh sync head has none until `ci_gate_run.py` runs on it).
   - **review_proof_on_head**: a non-degraded proof-of-review digest comment bound to the head SHA (a docs-only sync keeps it via `proof_neutral_carry`, default on; otherwise none until a review round posts one).
   - **fragility_clear**: the PR adds no fragile test (reads the step-6.4 run record for the head; see `skills/_shared/test-fragility.md`).

   This readout is **advisory**, like step 6.6; the blocking check of this skill is the step-6.7 sync gate, and the blocking land gate is `/tp-merge`.

   **Honest GitHub-UI bypass note**: A merge performed via the GitHub UI (clicking "Merge pull request") outside the tooling **bypasses** the land gate (this readout only reports it; `/tp-merge` enforces it). The branch-protection backstop (requiring a CI status check from `gate_cli.py` in a required workflow) is deferred to the `self-hosted-ci-runner` design (council verdict #6: branch-protection setup is deferred). Until that ships, the tooling-path gate is the only enforcement; operators should use `/tp-merge-from-main` to sync and the `/tp-merge` land skill to land the PR (not the GitHub UI) for merge operations on guarded branches.

7b. **Re-arm the ready ping (warn-never-block)**: after the step-7 push, run `python3 "$TP_ROOT"/skills/_shared/ready_ping_rearm.py --pr-url <pr_url> --head "$(git rev-parse HEAD)"` (the ping is recorded in the ping ledger), print its JSON line, and `PushNotification` the `ready_ping.message` when `ready_ping.status` is `sent`. Skip under `--dry-run` or `--no-push`. Fail-open: a non-zero exit never blocks the merge; a never-converged PR is a silent no-op.

8. **Post-merge auto-chain** (fires only when the design's completion PR has actually landed on `{base}`): after the step-7 push, check whether the archive is now present on `{base}` — guard: run `python3 "$TP_ROOT"/skills/tp-post-merge/scripts/verify_merged.py --repo . --design {design-name} --base {base} --json`; `merged == true` confirms the completion PR was merged to base. **`/tp-merge-from-main` itself does not land the completion PR** — it merges `{base}` *into* the design branch and updates the PR; the human (via the `/tp-merge` land skill, or a later `gh pr merge`) lands it. So in the ordinary base-sync invocation this guard is **false** and the step silently skips (see the last bullet). Only when `verify_merged.py` reports `merged == true` does this chain `/tp-post-merge {design-name}` (as `/tp-post-merge {design-name} --cheap-tier`, bare).

   - **Fail-open**: a teardown error from `/tp-post-merge` **never** undoes the merge. If `/tp-post-merge` fails, log the error and report it to the user — do not roll back anything. The merge already landed; cleanup can be retried manually with `/tp-post-merge {design-name}`.
   - **Skip under `--dry-run` or `--no-push`**: if either flag was passed, skip the auto-chain entirely (the merge did not actually happen or was not pushed).
   - **Additive and silent on non-completion merges**: if `verify_merged.py` reports `merged == false` (offline, unfetched refs, or this was just a base-sync merge, not a completion-PR merge), skip this step silently with no error.

## Rules

- **Validate `{design-name}`** per `skills/_shared/validate-name.md`.
- **Respect the lock** per `skills/_shared/collaboration.md` — `/tp-merge-from-main` rewrites tracked files and pushes.
- **Zero content drops is the hard gate.** The verifier is the backstop for *mechanical* drops; it is **necessary but not sufficient** (a semantic mis-merge can survive it), so semantic safety is carried by **deferral**, never by the verifier. Auto-resolution fires only when **mechanical-class ∧ classifier-confident ∧ verifier-passes**.
- **Merge, not rebase.** Rebase force-pushes the branch and strands parallel worktree agents that forked from the old HEAD. `/tp-merge-from-main` always merges.
- **Never disturb sibling worktrees.** The merge runs inside the design's own worktree.
- **Never auto-resolve code or prose.** Only the structured living-doc classes are touched; everything else is surfaced untouched. — a Fable-ruled living-doc hunk is applied only from a VERIFIED proposal (step 4); a code conflict is always the human's (`scope-growth`)
- **Optimize for zero-drop over reproducing past hand-merges** — the ground-truth human merge can itself be lossy (the spike's L4 case); a keep-both union that *diverges* from a lossy human result by preserving content is the correct answer.
- Use `mktemp` for any scratch files; the driver uses Python `tempfile` internally.
